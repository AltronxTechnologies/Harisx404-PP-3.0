## Authorization boundaries

- `middleware.ts` guards `/admin*` pages except login, requiring verified Supabase user and normalized `ADMIN_EMAIL`; `(dashboard)/layout.tsx` repeats that check. API routes are separate and must authorize each read/write method server-side. Client navigation and a protected page do not secure `/api/admin/*`.
- **Current source:** `app/lib/admin-auth.ts` calls `getUser()`, normalizes `ADMIN_EMAIL`, and returns 401 anonymous, 403 non-owner or 503 when Admin is unconfigured. Settings GET/PUT, About GET/PUT, FAQ reads/writes and Changelog/Media GET call it. FAQ list and edit-page reads plus all FAQ API methods use service role only **after** verified Admin; Settings and About create their service-role client after verification too. Changelog/Media retain their own data-client behavior; this is not a blanket claim about every Admin method or RLS policy.
- **Observed anonymous GET:** Settings/About/FAQs/Changelogs/Media now return 401 (Settings formerly 500; About/FAQs/Changelogs formerly 200). Earlier `/api/admin/experience` GET was 200 with no newer result here; earlier Testimonials/Resume/Buildlog/Community Wall GET 401 and Blogs/Projects GET 405 remain historical observations, not a current all-method audit. Inventory nested routes/server actions and test non-owner access before release. Status alone neither proves data exposure nor proves all verbs safe.
- **Observed owner-session GET:** `/api/admin/settings`, `/about`, `/faqs`, `/changelogs`, `/media` returned HTTP 200; only response shapes were recorded: Settings has seven named fields, About legacy fields, FAQs/Changelogs `data` arrays, Media `data` array/`count`. Dashboard and Logs list rendered under the read-only owner session. These observations do not verify other roles, CRUD, RLS policies or values.
- Service-role clients bypass RLS: never expose their key to browser; verify Admin before service-role reads or writes. Dashboard and Projects list follow this order in source and distinguish query errors from zero/empty; dashboard rendering does not verify count accuracy or draft visibility. Non-owner password sign-in calls `signOut()` in source; non-owner runtime flow remains unverified. Preserve named locks on Testimonials, Experience (entry 19), Certifications, Buildlog, Community Wall and the qualified Resume Admin document scope; no blanket unlock is implied.

## Risk register and gates

| Risk | Required gate before implementation/acceptance |
| --- | --- |
| Historical GET 200 / current 401 | Confirm intended visibility per method and public consumers; audit response shapes/RLS without recording values, including unchanged Experience behavior |
| Service-role or other mutation paths | Prove non-owner user rejected for every method/action; never rely on middleware; inventory unreviewed routes |
| Settings and Logs schema/provenance | Verify singleton save in isolated DB; `resolved` now queries successfully, so inspect connected schema/index provenance and policies before deciding whether any Logs migration step is necessary |
| Broad FAQ/site-settings RLS policies | Inspect connected policy catalog before applying staged hardening; verify public read and non-owner write behavior afterward |
| Legacy About / unused Changelog editor | Do not promise public updates from these Admin writes; owner decides retirement/repurpose without touching locked public presentation |
| Media schema and upload assumptions | Keep observed `bytes`/`alt_text`/`secure_url` mapping; do not invent a server size cap or assert upload/delete success from read-only GET or source UI |
| Accidental publishing, cache staleness or destructive cleanup | Test draft/published boundaries, dependent assets, atomicity/revalidation and rollback on disposable records only |
| Public/locked-scope regression | Explicit owner unlock for named locked Admin files; no global/shared edits or indirect public presentation changes without authorization |
| Root chrome/metadata and masked Admin overflow | Owner decides isolation without unapproved root changes; inspect element bounds as well as document scroll; named Buildlog Admin unlock required before fixing its measured overflow |
| Leaking secrets through logs, errors or fixtures | Redacted errors, least-privilege keys, no actual values in evidence, no credentials in recordings |

**Owner/manual gates:** the supplied owner session authorizes read-only observation only; separately approve Settings/About save-reopen, Media interaction/mutations, policy-catalog review and any SQL rollout/rollback, and disposable fixtures/cleanup. Named permission remains required for Experience, Testimonials, Certifications, **Buildlog Admin overflow**, Community Wall or qualified Resume Admin work. Root layout isolation needs explicit owner unlock or approved alternative. Connected saves, uploads, deletions, log actions and production-readiness claims remain blocked.
