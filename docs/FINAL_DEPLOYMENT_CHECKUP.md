## One-Page Checkup Protocol

For an owner request such as "final checkup `/projects`", use this sequence and do not substitute another page's PASS:

1. **Freeze baseline.** Record date, commit, branch, dirty files, target URL/environment, related locks, approved design screenshot and page dependencies. Capture desktop/mobile/dark/light baseline before changing UI. Identify actual content source and what can be safely mutated. Recheck route inventory if files changed.
2. **Map route and states.** Read its page/layout/loading/error/not-found, metadata, data queries, actions/endpoints, shared components and tests. Enumerate controls, keyboard/touch alternatives, data/auth/permission flows, empty/loading/error/success/retry/stale paths, outbound links and assets. Note where middleware, provider, DB and caching can affect it.
3. **Functional browser matrix.** Direct URL, internal navigation, back/forward, refresh, query/filter/pagination, invalid/missing IDs, redirects/trailing slashes, link/download/copy/form/modal/search/carousel/animation controls, disabled/duplicate-click behavior and correct content. Use approved disposable records for create/edit/publish/unpublish/delete and prove public propagation. Test timeout, invalid body, expired session and provider outage safely. Record HTTP status and redacted network/console evidence; streaming fetch shells are not direct document 404 proof.
4. **Design without redesign.** At 320, 375, 390, 430, 768, 1024, 1280, 1440 and a wider screen where meaningful: light/dark, long content, zoom/text resize, reduced motion, empty/loading/error states and touch. Measure viewport overflow, clipped/obscured content, image dimensions/alt/crop, section rhythm, card alignment, sticky nav/footer and CLS. Compare against the *approved* baseline and `DESIGN_DEBT.md`; preserve intentional differences. Keep screenshots out of the repo unless approved. List subjective suggestions for owner approval; do not implement them.
5. **WCAG 2.2 AA.** Check semantic landmarks/headings, labels/errors/live regions, skip link, tab/focus order and return, modal trapping/dismissal, screen-reader names, contrast (4.5:1 text, 3:1 large text/UI), 24px target-size minimum or allowed exceptions, focus not obscured, non-drag alternative, 200%/400% zoom, motion controls and no color-only status. Run an automated scan where available **and** manual keyboard/assistive-technology checks; mark missing manual verification BLOCKED.
6. **Security, data and reliability.** Verify server authorization independent of UI; CSRF/IDOR/injection/XSS/SSRF/open redirects relevant to this route, request size/rate limit, safe uploads, secure cookies/headers, no server-only secrets in client HTML/JS/logs, appropriate RLS/grants, stale-write/conflict and rollback. Audit async races, error boundaries, hydration, cleanup, loading stop, truthful success and safe retry. Test permitted negative cases without touching live data.
7. **Discoverability and speed.** Public route: unique factual title/description, HTTPS canonical, OG/Twitter asset, robots/sitemap/RSS eligibility, appropriate JSON-LD and status for missing/draft, crawlable links, accurate claims; do not promise search/LLM ranking. Measure production-mode lab LCP/FCP/CLS/TBT, image/font and JS transfer on representative mobile/desktop network; compare pre/post on same conditions. Field p75 LCP <=2.5s, INP <=200ms, CLS <=0.1 is a separate deployed data check, not a Lighthouse score.
8. **Reproduce, plan, fix, retest.** File each evidenced issue using the template below, prioritize P0/P1 before P2/P3. Draft tasks with dependencies, tests, acceptance and rollback. Fix safe in-scope nonvisual defects; request approval for material visual/locked changes and consequential operations. Run focused and dependent regression tests, static checks and isolated build. Recheck that exact issue in browser and compare before/after. Do not silence failures or invent assertions merely to pass.
9. **Independent sign-off.** Reread diff, verify unchanged routes sharing components, confirm original and negative paths, revisit every finding and missing gate, and record route-specific statuses. A page is **locally verified** only if its required local checks pass; **production-ready** additionally requires connected staging evidence, no open blocker in its dependencies, owner content/design approval and whole-site release gates. Store page report under `docs/final-checkups/<route-name>.md` only when the checkup is actually performed.

### Page Report Template

```text
Route(s), exact slug/fixture, environment and URL, date, commit, reviewer:
Baseline locks/screenshot reference; owners of external dependencies:
Source map: page, layout, shared components, data/actions/API, tests:
Controls and state inventory: [control | action | success | failure | keyboard/touch | evidence]
Results: function [PASS/FAIL/BLOCKED/NOT APPLICABLE]; responsive/visual [...]; console/network [...]; WCAG [...]; SEO [...]; security [...]; performance lab [...]; deployed/field [...].
Evidence: commands/results, HTTP/status, viewport/theme/device, screenshot location (outside repo), redacted logs, test names, measured values.
Findings: ID, class, P0-P3, route/file, observed vs expected, reproduction and evidence, root cause/unknown, proposed and actual fix, focused/regression result, rollback, status.
Plan: task ID, linked finding, priority, impact, files, dependencies, implementation, tests, acceptance, rollback, owner/approval, status (pending/in progress/blocked/implemented/verified/rejected).
Blocked: what is missing, why needed, owner, next verification step.
Visual proposals (approval required): ID, defect vs suggestion, current/proposed, evidence, benefit, risks, owner decision.
Final route verdict and remaining whole-site gates; no implicit carryover PASS.
```

## Whole-Site Release Sequence

1. Confirm exact Vercel target, canonical HTTPS host, owner/branch and approved scope. Review Git diff, locks, legal/content rights and current secrets privately; rotate exposed credentials. No automatic deployment.
2. Inventory installed Supabase schema, migrations, triggers, RLS, grants and storage; take backup and **prove restore** of DB, Auth, private Storage, Cloudinary originals and configuration on a separate target (`docs/admin-redesign/08-backup-restore.md`). 3. In isolated Docker/clean checkout use npm lockfile and reviewed safe tests, TypeScript, lint, security triage and `NEXT_DIST_DIR=.next-build` build. Do not overwrite running `.next`; preserve exact results/skips and remove validation artifacts.
4. Run approved disposable DB/Auth/API/upload/provider tests, browser route matrix and failure/concurrency cases; record separate function, responsive/visual, console/network, WCAG, SEO (public) and security (Admin) statuses for every actual route. Make focused fixes, then independently rerun affected and cross-route checks. No unapproved design changes.
5. Produce a Vercel preview/staging deployment through the **confirmed** Git integration only after permission. Validate real host callbacks, headers/CSP compatibility, publication/cache, 404, forms, assets, content/SEO/AI and rollback with test accounts; obtain controlled lab measurements and later field p75 when available. Diagnose backend and third-party errors from redacted telemetry.
6. Owner checkpoint: review findings, visual proposals, connected recovery evidence, secrets, actual domain, environment settings and residual risk. Choose exactly one verdict: `READY FOR DEPLOYMENT`, `NOT READY - RELEASE BLOCKERS REMAIN`, or `BLOCKED - REQUIRED ACCESS OR VERIFICATION IS UNAVAILABLE`. READY requires all P0/P1 gates closed with evidence; a local build alone never qualifies.
7. After **explicit** deployment approval, use the verified Vercel project/branch workflow. Immediately smoke public, admin, metadata, Auth, forms, media, cache and monitoring on production. On failure use Vercel Instant Rollback to an eligible previous deployment **and** the reviewed data recovery/forward-fix plan; Vercel rollback does not revert environment variables, databases, Storage or Cloudinary. Verify the domain assignment after rollback and communicate the incident.
