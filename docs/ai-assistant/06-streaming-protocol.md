**Component:** `app/api/ai/chat/route.ts` & `app/components/ChatbotWidget.tsx`

## 1. Executive Summary

Phase 5 introduces progressive Server-Sent Events (SSE) streaming to the AI portfolio assistant without introducing fragile client dependencies or compromising reliability. The implementation enforces strict failover boundaries: secondary provider fallback (Gemini) is allowed **strictly before** any token is emitted to the client stream. If a stream is interrupted after partial output, the server emits an explicit error event rather than silently stitching together two disjoint model outputs.

A complete deterministic non-streaming baseline (`JSON { text }`) is retained for automated testing and clients that do not request streaming.

## 2. Protocol Specification

### 2.1 Transport & Headers
- **HTTP Method:** `POST`
- **Request Headers:**
  - `Content-Type: application/json`
  - `Accept: text/event-stream`
- **Request Body:**
  ```json
  {
    "messages": [
      { "role": "user", "content": "Tell me about Haris" }
    ],
    "stream": true
  }
  ```
- **Response Headers:**
  - `Content-Type: text/event-stream; charset=utf-8`
  - `Cache-Control: no-cache, no-transform`
  - `Connection: keep-alive`
  - `X-Accel-Buffering: no` (disables buffering on reverse proxies/nginx/Vercel)

### 2.2 Event Framing
Events follow the standard SSE specification:
```
event: <eventType>
data: <jsonPayload>

```

Supported Event Types:
| Event Type | Payload Format | Description |
|:---|:---|:---|
| `start` | `{"provider": "groq" \| "gemini"}` | Emitted immediately when the first provider token arrives. |
| `delta` | `{"text": string}` | An incremental text token generated by the model. |
| `done` | `{"totalLength": number}` | Signals normal generation completion. |
| `error` | `{"code": string, "message": string}` | Signals generation failure (e.g. `STREAM_INTERRUPTED`, `UNAVAILABLE`). |

## 3. Provider Failover & Mid-Stream Interruption Invariant

A critical defect in naive streaming architectures is silently falling back to a second model after partial tokens have already been emitted, producing nonsensical blended responses.

Phase 5 enforces this boundary in code:
```ts
// 1. Primary: Groq Streaming
if (groqKey) {
  try {
    ...
  } catch {
    // If Groq failed after partial output, do NOT mix in Gemini!
    if (tokensEmitted > 0) {
      sendEvent('error', {
        code: 'STREAM_INTERRUPTED',
        message: 'Connection was interrupted while generating. Please retry.',
      });
      controller.close();
      return;
    }
  }
}

// 2. Secondary: Gemini Fallback (Allowed ONLY if Groq emitted 0 tokens)
if (tokensEmitted === 0 && (process.env.GOOGLE_AI_API_KEY || process.env.GEMINI_API_KEY)) {
  ...
}
```

## 4. Client-Side Stream Parser & Buffer Strategy

Network packets arrive in arbitrary sizes and may split JSON lines, SSE event boundaries (`\n\n`), or multi-byte UTF-8 glyphs (e.g. emojis).

### 4.1 Incremental Buffering
The client reader in `app/components/ChatbotWidget.tsx` implements:
1. `decoder.decode(value, { stream: true })` to preserve partial multi-byte UTF-8 sequences.
2. An event accumulator that splits on `\r?\n\r?\n` and retains the incomplete trailing slice in `buffer` across `read()` calls.
3. Post-stream flush with `decoder.decode()` to process any trailing buffer contents.

### 4.2 User Cancellation ("Stop" button)
1. Each request creates a scoped `AbortController` stored in `abortRef.current`.
2. When the visitor clicks "Stop" or closes the widget:
   - `abortRef.current.abort()` cancels the fetch reader.
   - Stream reader cancels without unhandled promise rejections.
   - Any accumulated response text remains visible in the conversation history without throwing a red error card.
