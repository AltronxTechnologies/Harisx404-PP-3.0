# End-to-End Type Safety: Building a Type-Safe MERN Application

End-to-end type safety means the shape of your data is checked from the database to the browser, so a change in one place breaks the build instead of breaking production. In a MERN app (MongoDB, Express, React, Node) the honest version has one extra rule: TypeScript types disappear at runtime, so every boundary where outside data arrives also needs a runtime check.

This guide shows a practical setup: one schema package shared by the API and the client, validation at each boundary, and a thin mapping layer between your database and your API. It ends with the mistakes that most often undo the whole idea.

## The core idea: schemas as the source of truth

A type like `type User = { id: string }` describes what you hope the data looks like. A runtime schema checks what the data actually is, and can produce the type for you. [Zod](https://zod.dev/v4/changelog) is a popular choice for that, and Zod 4 is now stable. Define a schema once, infer the type from it, and import both on the server and in the browser.

A note on tooling, because it moved this year: TypeScript 6.0 shipped in March 2026 as the last release on the old JavaScript codebase, and [TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) arrived on July 8, 2026 as a native port that Microsoft describes as roughly 8x to 12x faster on full builds. TypeScript 7.0 doesn't yet ship a stable programmatic API, so tools that rely on it, such as typescript-eslint, Vite integrations, and Nx, may need TypeScript 6 installed beside it, as [Nx's guide](https://nx.dev/docs/technologies/typescript/guides/typescript-7) describes. Everything below works the same on either version. Turn on `strict` mode.

## A shared contracts package

Put schemas in a workspace package that both apps import, for example `packages/contracts`:

```ts
// packages/contracts/src/todo.ts
import * as z from "zod";

export const TodoId = z.string().regex(/^[a-f\d]{24}$/); // a MongoDB ObjectId as hex

export const CreateTodoBody = z.strictObject({
  title: z.string().trim().min(1).max(120),
  dueDate: z.iso.datetime().optional(),
});

export const TodoDto = z.strictObject({
  id: TodoId,
  title: z.string(),
  done: z.boolean(),
  dueDate: z.iso.datetime().nullable(),
});

export type CreateTodoBody = z.infer<typeof CreateTodoBody>;
export type TodoDto = z.infer<typeof TodoDto>;
```

`strictObject` rejects unknown keys, which catches typos and stops callers from smuggling in extra fields. Notice that the DTO (data transfer object, the shape that crosses the network) is separate from the database document. You'll see why below.

## The API: validate in, shape out

Express 5 forwards errors thrown in async handlers to your error middleware, so handlers don't need try/catch wrappers ([migration guide](https://expressjs.com/en/guide/migrating-5.html)). Start with a typed error and one place that turns it into a response:

```ts
// apps/api/src/http-error.ts
import type { NextFunction, Request, Response } from "express";

export class HttpError extends Error {
  constructor(
    public status: number,
    public code: string,
    public details?: unknown,
  ) {
    super(code);
  }
}

// Express recognizes error middleware by its four parameters.
export function errorHandler(err: unknown, _req: Request, res: Response, _next: NextFunction) {
  if (err instanceof HttpError) {
    return res.status(err.status).json({ error: { code: err.code, details: err.details } });
  }
  console.error(err);
  return res.status(500).json({ error: { code: "internal_error" } });
}
```

Typing the authenticated user once means handlers never reach for a cast:

```ts
// apps/api/src/auth.ts
import type { Request } from "express";
import { HttpError } from "./http-error";

declare module "express-serve-static-core" {
  interface Request {
    auth?: { userId: string }; // set by your authentication middleware
  }
}

export function getAuth(req: Request): { userId: string } {
  if (!req.auth) throw new HttpError(401, "unauthenticated");
  return req.auth;
}
```

Now a route that validates the body, creates the document, and returns the DTO:

```ts
// apps/api/src/todos.ts
import { Router } from "express";
import * as z from "zod";
import { CreateTodoBody } from "@acme/contracts";
import { getAuth } from "./auth";
import { HttpError } from "./http-error";
import { Todo, toTodoDto } from "./todo.model";

export const todos = Router();

todos.post("/", async (req, res) => {
  const parsed = CreateTodoBody.safeParse(req.body);
  if (!parsed.success) {
    throw new HttpError(400, "invalid_body", z.flattenError(parsed.error));
  }
  const { userId } = getAuth(req);

  const doc = await Todo.create({
    ownerId: userId,
    title: parsed.data.title,
    dueDate: parsed.data.dueDate ? new Date(parsed.data.dueDate) : null,
  });

  res.status(201).json(toTodoDto(doc));
});
```

Mongoose [recommends relying on automatic type inference](https://mongoosejs.com/docs/typescript/schemas.html) from your schema definition, so you rarely need to write a separate interface for the model:

```ts
// apps/api/src/todo.model.ts
import { Schema, model } from "mongoose";
import type { TodoDto } from "@acme/contracts";

const todoSchema = new Schema(
  {
    ownerId: { type: String, required: true, index: true },
    title: { type: String, required: true, maxlength: 120 },
    done: { type: Boolean, default: false },
    dueDate: { type: Date, default: null },
  },
  { timestamps: true },
);

export const Todo = model("Todo", todoSchema);

// The mapping layer: database shape in, API shape out.
export function toTodoDto(doc: {
  _id: { toString(): string };
  title: string;
  done: boolean;
  dueDate?: Date | null;
}): TodoDto {
  return {
    id: doc._id.toString(),
    title: doc.title,
    done: doc.done,
    dueDate: doc.dueDate ? doc.dueDate.toISOString() : null,
  };
}
```

This mapper is the reason the DTO is its own type. A database document has `_id` as an ObjectId, `Date` objects, and fields like `ownerId` that clients should never see. The mapper converts explicitly, so the compiler checks every field that crosses the boundary, and an accidental new database column never leaks to the wire.

One Express 5 detail matters for validation middleware: `req.query` is now a read-only getter, and the default query parser is "simple." Parse it into a new variable (`const query = ListQuery.parse(req.query)`) instead of trying to overwrite the request.

## The client: don't trust the network either

TypeScript can't know what a `fetch` returns. Validate responses with the same schema:

```ts
// apps/web/src/api.ts
import * as z from "zod";
import { CreateTodoBody, TodoDto } from "@acme/contracts";

async function request<S extends z.ZodType>(
  path: string,
  schema: S,
  init?: RequestInit,
): Promise<z.output<S>> {
  const res = await fetch(`/api${path}`, {
    ...init,
    headers: { "content-type": "application/json", ...init?.headers },
  });
  if (!res.ok) throw new Error(`Request failed with status ${res.status}`);
  return schema.parse(await res.json());
}

export const createTodo = (body: CreateTodoBody) =>
  request("/todos", TodoDto, {
    method: "POST",
    body: JSON.stringify(CreateTodoBody.parse(body)),
  });
```

If the API and client ever drift, you get a clear parse error at the boundary instead of a mysterious `undefined` three components later.

## Test the contract, not just the compiler

A green build proves the types line up. It doesn't prove that the running API returns what the types promise. A small contract test closes that gap, and Node's built-in test runner is enough:

```ts
import test from "node:test";
import assert from "node:assert/strict";
import * as z from "zod";
import { TodoDto } from "@acme/contracts";

test("GET /api/todos matches the contract", async () => {
  const res = await fetch(`${process.env.API_URL}/api/todos`, {
    headers: { authorization: `Bearer ${process.env.TEST_TOKEN}` },
  });
  assert.equal(res.status, 200);
  z.array(TodoDto).parse(await res.json()); // throws with details if the shape drifted
});
```

For hot paths in production you may skip response validation to save time, but keep it on in development and in tests.

## Common mistakes

- **Casting at the boundary.** `req.body as CreateTodoBody` silences the compiler and checks nothing. Parse instead.
- **Returning database documents directly.** It leaks internal fields and ties your API to your storage layout.
- **Duplicating schemas by hand** on the client and server. They drift. Share the package.
- **Forgetting serialization.** Dates and ObjectIds become strings over JSON. Model that in the DTO.
- **Treating `lean()` results as hydrated documents.** They lack methods and virtuals, so type them for what they are.
- **Stopping at "it compiles."** Add the contract test above.

The same habit applies anywhere untrusted data meets code, including the arguments an AI model passes to a tool, as shown in [securing AI agents](/blog/securing-ai-agents). If your front end is Next.js rather than a standalone React app, the contract approach carries over to Server Actions and route handlers, and [Next.js 16's caching model](/blog/nextjs-16-cache-components) changes where data is read.

## Key takeaways

- Types vanish at runtime. Put a schema check at every boundary.
- Share one contracts package, and infer types from the schemas.
- Keep DTOs separate from database documents, and map between them explicitly.
- Express 5 forwards async errors, and `req.query` is read-only.
- Test the contract with real parses, not just compilation.

## Frequently Asked Questions

### Does TypeScript validate request bodies at runtime?

No. TypeScript only checks code at compile time. A request body arrives as unknown data, so validate it with a runtime schema library before treating it as typed.

### Do I need both Mongoose schemas and Zod schemas?

They serve different purposes. The Mongoose schema describes storage and database-level rules. The Zod schema describes the API contract. Keeping them separate, with a mapper between them, avoids leaking storage details.

### Is Zod the only option?

No. Other schema libraries exist, and the pattern (runtime schema plus inferred types) matters more than the brand. Zod is widely used and works well with the approach shown here.

### Should I use Express 5 or stay on Express 4?

Express 5 is the current major release and handles rejected promises in async handlers automatically. Review the migration guide, especially changes to `req.query`, before you upgrade.

### How do I share types in a monorepo?

Create a workspace package (for example `packages/contracts`) that exports schemas and inferred types, and add it as a dependency of both the client and the API.
